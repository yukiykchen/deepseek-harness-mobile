### 2.6 Kuikly reactive/theming research (this session) — read this before Task 1
Read from `kuikly-ui/core/src/commonMain/kotlin/com/tencent/kuikly/core/`. These four facts decide the whole Task 1 design:
1. `ReactiveObserver` collects dependencies **per pager**, keyed by `"${propertyOwner}_$propertyName"`, and the key is **owner-agnostic** — reading *any* object's `observable` property inside a reactive closure registers the dependency. So reading a property that lives on the `Pager` from inside a deeply nested child's closure is reactive. No plumbing needed.
2. `DeclarativeBaseView.attr(init)` binds `init` through `ReactiveObserver.bindValueChange(this)`, so **the whole `attr { }` closure re-runs** when anything it read changes. `attr {}` is the reactive unit.
3. `Props : BaseObject(), IPagerId` and `IPagerId : PagerScope`, and `internalCreateAttr()` does `attr.pagerId = pagerId`. **Therefore inside every `attr { }` block, `this` is already a `PagerScope` with a valid `pagerId`.** That makes this the whole access mechanism:
   ```kotlin
   internal val PagerScope.theme: DshPalette
       get() = (getPager() as? BasePager)?.palette ?: DshTheme.light
   ```
   With that, replacing `color(Color(0xFF1F2933))` with `color(theme.textPrimary)` inside an `attr {}` is a purely mechanical, reactive edit — no new parameters on any of the `ViewContainer<*, *>.DshXxx(...)` helpers, no new attrs on the `ComposeView`s. **Do it this way.**
4. `ComposeView.didInit()` calls `body()()` **once**. Anything read in `body()` *before* the returned builder lambda is read once and is not reactive (existing examples: `DshLongTextView.body()` reads `ctx.attr.expanded`, `DshJobsPanelView.body()` snapshots `ctx.attr.jobs`). Don't put `theme` reads there; put them inside `attr {}`.

Verify (1)–(3) empirically the first time you toggle the theme on the emulator; if a surface doesn't repaint, the cause is almost always a `theme` read that landed outside an `attr {}`.

Point 4 was **confirmed the hard way**: `DshQuestionFlowView.body()` read the current question once, so paging a 2-question waterfall advanced the options but not the header/question/detail. Fixed in `008e4cf` by reading it inside `attr {}`. Treat that as proof, and never read mutable attrs in `body()`.

### The 0.1.5-only decision, and why the task's reference links are dead

The requirements doc points at `packages/host/apiproxy/src/api/sessions.ts` and friends on `master`. **That package no longer exists**, so every one of those links 404s today and the exercise was evidently authored in the 0.1.1 era. Verified in the upstream clone two independent ways:

- **Package layout.** `git ls-tree dsh-v0.1.1-rc.2 packages/host/` lists `apiproxy`; `git ls-tree HEAD packages/host/` does **not** — it was replaced by `packages/api/{gateway,session-controller,workspace-controller}`.

So the endpoint was **deleted, not moved**, and the old `/api/events.mux` + `Authorization: Bearer` transport cannot reach a current `dsh web`.

Protocol in `docs/dsh-mobile-admin-protocol.md`.

**Findings from the upstream research that decided this stage — do not re-derive them:**
- **A `webServer` route is NOT authenticated.** First-party plugins gate themselves with `ctx.connection.requestRejection(req)`, which is the Host/Origin fence (403) plus the browser-cookie check (401); `packages/host/open-in-app/src/index.ts:184` is the pattern. Ours does the same. **Loopback is not authentication** — the phone reaches loopback through the pairing tunnel, and so does every other process on the machine, so a loopback-only check would leave the route open to anything running locally.
- **Unarchive cannot be done safely from a plugin.** `WorkspaceRegistry` (`packages/workspace/workspace/src/index.ts:226-254`) has `archiveSession` and an `archivedSessionIds` getter and no removal; upstream's README says "Archiving is one-way". The set is in `$DSH_HOME/storages/workspace.json`, but the registry caches it and writes `{...this.state, archivedSessionIds: […]}`, so a direct write is invisible to the running Host and gets discarded by the next legitimate write. **Declined on purpose** (user decision, §7 plan) rather than shipped as a data-loss bug. Note that `workspace/unarchiveSession` and `workspace/deleteSession` are not endpoints any Host serves, so calling them would achieve nothing either.
- **Permanent delete is worse:** no delete at any layer, and a purge touches five artifacts including attachments shared by hash across sessions.
- Loader writes that do work: `entry.update({disabled})`, `loader.create/remove/update`, `loader.await()`. There is **no** `loader.reload` — reload is a disable/enable pair.

**App side:** `DshHostConnectionRuntime.callPath` (POST outside `/api`, plugin `{ok,value|error}` envelope, no generation queueing, 401 still triggers the re-mint), `probePluginAdmin` (capabilities-advertised, never probe-by-error), `controlPlugin`, a generic `DshConfirmModal`, and per-row controls that appear only for entries the plugin marks controllable.

**Mock host:** serves `/dsh-mobile/*` by calling the plugin's **own** `dispatch` with only the loader faked, and `pluginInventory/list` now projects from that same fake loader — so a lifecycle change is visible to both, exactly as on a real Host.
